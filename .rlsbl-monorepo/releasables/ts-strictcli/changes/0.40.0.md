## 0.40.0

The declaration-regime release: mandatory presence declarations, scoped selectors replacing mutex groups, real-JSON-Schema value fragments (schema v2), the co-occurrence constraint system, and the update-command construct.

<details>
<summary>Context</summary>

The declaration-regime campaign closes the last places where strictcli inferred something the developer had not written down: presence is now declared on every flag and arg, exactly-one selection is a scoped choice flag rather than a mutex group, `--dump-schema` publishes real JSON Schema value fragments at schema version 2, co-occurrence rules are one named constraint container, and an update command declares the resource, write mode, identity and properties it writes. Consumers must migrate their declarations before adopting this version: the new rules are registration-time hard errors, so an unmigrated app fails to build rather than misbehaving, and a repo that has not migrated simply stays on the previous floor until it does.

</details>

### Breaking

- [ts-strictcli] **Presence is now declared, never inferred.** `FlagOpts` is a discriminated union on `presence`: every flag declares exactly one of `{ presence: "required" }`, `{ presence: "optional" }` or `{ presence: "default", default: <value> }`, and `ArgOpts` moves onto the same union with `required?: boolean` deleted. Declaring none or two is a registration-time error, `default: null` is refused with a redirect to `presence: "optional"`, a list or dict flag no longer defaults silently to `[]` / `{}`, a variadic arg cannot declare a default, and a mutex member declares its own optionality instead of receiving a parse-time exemption. An optional flag or arg delivers `undefined` (bools become a real tri-state), and the inferred handler-args type follows the declaration -- which fixes the mutex-member key that was typed as always-present while the parser handed it `undefined`.
- [ts-strictcli] **Choices are a declaration scope.** `choiceFlag(name, choices, opts)` declares a flag whose type is its set of choices, each declared with `choice({ help, flags?, value? })` and owning the flags that exist only while it is elected. The handler receives one tagged value under the selector's own key -- a discriminated union derived from the literal choice map, so `switch (args.via.choice)` narrows and `assertNever` in the default branch is checked by the compiler, with no annotation written anywhere. Sub-flags are never top-level handler arguments at any depth, `provided(record, name)` answers provided-ness inside a scope, nesting is unlimited, and parsing is order-independent: `--subject hi --via email` parses exactly as `--via email --subject hi` does. A flag supplied outside its elected scope is its own parse error naming the flag, its owning choice and the choice that was elected -- never "unknown flag". A selector declares `required` or a `default` and never `optional`, a defaulted selection must be complete, and `choices` entries become `{ value, help? }` records with the bare-value spelling deleted -- `choices: ["a", "b"]` becomes `choices: [{ value: "a" }, { value: "b" }]`, and a flag whose entries carry help renders as an indented block instead of the one-line `[choices: a, b]` form.
- [ts-strictcli] **`mutexGroup` is removed.** Exactly-one-of-these is a member-spelled choice flag now: `memberChoiceFlag(name, choices, opts)` spells each choice as its own flag carrying its own payload, and it reproduces the mutex error sentences and the `--no-x` decline semantics byte-for-byte. There is no shim and no deprecation period -- replace `mutex: [mutexGroup({ a, b })]` with a `memberChoiceFlag` entry in the command's `flags` map. A member gains what a group could not express: a scope of its own, so `--profile work --create-missing` parses and `--all-profiles --create-missing` is a scope error, and a payload carried in the alternative that owns it, so the sentinel defaults on flags that meant nothing unless elected disappear. The handler receives one tagged record instead of one value per member, a member flag is `required once this member is elected` (inverting the rule that forbade requiredness on a member), and the `Flags (mutually exclusive):` help section is gone with the construct. Constraints now operate at root scope only: naming a scoped flag from `allOrNone`, `atLeastOne`, `requires` or `implies` is a registration error, because the scope already is the constraint.
- [ts-strictcli] **`--dump-schema` writes schema version 2.** A flag or arg entry carries a real JSON Schema fragment under `value_schema`, from a closed subset of `type`, `items`, `additionalProperties` and `enum` with JSON Schema's own type names; the `type` key and the `repeatable` key are gone, because arity is a property of the value and a variadic arg publishes the same array fragment a `list[T]` flag does. A value flag's `choices` splits in two: the values as an `enum` inside the fragment, and the value-plus-help records beside it under `choices` (`help` omitted when an entry declares none). A choice flag has no fragment at all -- its value is a variant the subset cannot express -- and instead publishes its nested choices and scopes, each scoped entry a full flag entry, with `elect_by` as the discriminator. Every entity's keys are emitted in a declared order, the document is written in one canonical encoding so two implementations' dumps are byte-comparable, and the `defaults` block is rewritten as the complete map of what an omitted key means. The dump also stops being blind to behavior: `config_format`, `config_path`, `config_conflict_mode`, per-flag `prefixed` and per-command `flag_sets` each appear exactly when a declaration departs from the framework's own behavior, `config_path` publishes the declaration rather than the machine's resolution of it, and the `checks` block is a function of the declaration alone.
- [ts-strictcli] **`provided()` over a caller-supplied elected record now answers `false` for every field.** The record door labels every field it delivers as the declaration's, so a handler can no longer tell a field the call supplied from one the declaration filled. The command line is unaffected and still answers what the invocation caused.
- [ts-strictcli] **Constraints, reshaped.** `coRequired` is deleted and `allOrNone` takes its place beside a new `atLeastOne`, both taking one option object with a mandatory `name` and passed through `constraints: [...]`. A member is a plain `{ name, when? }` record naming a flag, a positional arg or another named constraint, nested to unlimited depth; `members` is typed `[M, M, ...M[]]`, so a one-member constraint is a compile error, and `when` is the literal union `"present" | "true" | "non_empty"`, so a typo is one too. A bool member must declare its election, so `--no-x` can no longer engage a constraint while selecting nothing. `requires` and `implies` keep their semantics and take the same mandatory name. No member may declare `presence: "required"`. Constraints now render in `--help`, publish their members in `--dump-schema`, and project into MCP tool schemas as `anyOf` / `dependentRequired` with any remainder stated in the tool description.
- [ts-strictcli] **Three breaking changes, all of them the update-command round's.** (1) The mutating-default ban: a flag or positional arg on a command declaring `effect: "mutating"` may no longer declare a value default, because on a mutating command a value the framework picked is a value the framework writes -- empty collection defaults, `relativeToRoot()` defaults, a choice flag's own default and every declaration on a read_only command stay legal. (2) `config set` takes its value under `--value`: its write is now an exactly-one selection over a value, a clear and a reset to default (`config set <key> --value <v>`), and supplying none or two of the three is refused by the framework rather than by the command. (3) The machine envelope gains a `writes` member carrying an update command's write set, and `interface_version` becomes `2`.

### Features

- [ts-strictcli] **`ctx.provided(name)`, and presence published everywhere it is asked about.** `ctx.provided` answers whether the invocation caused a flag's value -- true for `cli`, `env`, `config` and `implied`, false for `default` and `infra` -- so no handler reconstructs that boolean out of `ctx.source`. `--dump-schema` emits a `presence` key on every flag and arg entry plus a `default` exactly when presence is `"default"` (empty collections included), and the arg entry's `required` key is gone; help renders exactly one presence marker per line (`[required]`, `[optional]` or `[default: <value>]`), with required positionals and declared empty collections now visible; and MCP tool schemas read requiredness straight off the declaration, so a required bool finally appears in `required`.
- [ts-strictcli] **README explains the TypeScript-shaped declaration surface.** The package README now states that the TypeScript implementation is not a port of the Python or Go ones: flag and arg options are a discriminated union on `presence` (a `default` beside `presence: "required"` does not compile, and `presence: "default"` without a `default` does not either), the twin command factories narrow the handler's `ctx` so a `.write()` inside a read-only command is a compile error, and what the three implementations hold identical is behavior rather than spelling.
- [ts-strictcli] **The scope rule reaches the type system and the machine boundary.** A computed choice key is a compile error naming itself (it would silently degrade the delivered tag to `string` and make `assertNever` accept anything), a selector's `default` is typed `keyof C & string` so naming a choice that does not exist fails to compile before it fails to register, and a scoped sub-flag is unreachable as a top-level handler argument -- which is the structural fix for the handler-args unsoundness the mutex-member shape carried. Over MCP one command is still one tool: the selector contributes an `enum` property, every scoped flag contributes a top-level property that never appears in `required` (its requiredness is conditional), and the scope structure rides the tool description as a deterministic `Scoped parameters (enforced at call time):` block. A wrong combination is refused at call time with the same sentence the CLI parser gives.
- [ts-strictcli] **An integer `choices` entry beyond ±2^53 is refused at registration.** The dumped schema publishes a declaration's choices as a JSON Schema `enum`, and a reader that parses JSON numbers as IEEE-754 doubles -- which every reader of a schema file is entitled to be -- reads a different integer back. Declare a big identifier as a string instead. Float choices are unaffected: the canonical float form round-trips exactly, so nothing is lost there.
- [ts-strictcli] **A variadic positional arg accepts a list carrier.** `arg("files", t.list(t.str), { variadic: true, ... })` registers beside the element-carrier spelling `arg("files", t.str, { variadic: true, ... })`; both deliver the same array and publish the same schema fragment. The element spelling stays legal and stays the idiomatic one -- this widens the surface, it does not replace it. A list carrier on a non-variadic arg is still refused, and a dict carrier is refused on both.
- [ts-strictcli] **A choice name must match `[a-z][a-z0-9-]*`, checked at registration.** A choice name is a surface name whatever elects it -- a token-spelled choice flag publishes it in an enum, a member-spelled one puts it on the command line as a flag -- and TypeScript spells it as a property key of the choice map, which constrains nothing. `choice({...})` under a key like `Email`, `e_mail` or `1email` is now refused with `Flag "via": choice name "Email" must match [a-z][a-z0-9-]*` in both spellings, before member spelling's flag-name bans, so a name that fails both is reported as the charset failure it is.
- [ts-strictcli] **The README documents the choice flag.** A new section shows `choiceFlag`/`memberChoiceFlag` and `choice`, the derived discriminated union a `switch` narrows with `assertNever`, the compile-checked `default` typed `keyof C & string`, and the fact that `optional` has no union member at all; the feature list gains a choice-flag entry and drops the retired mutex one.
- [ts-strictcli] **The README documents the constraint system.** A Constraints section covers the four factories and their mandatory names, the `{ name, when? }` member object, the `members` tuple and `when` literal union that make a one-member constraint and a selector typo compile errors, the mandatory bool election, nesting with the help block it renders, the required-member refusal, and the root-scope rule.
- [ts-strictcli] **The update-command construct.** `updateOf: { resource, writeMode, identity, properties }` on a command spec declares what a command updates: which flags and args name the instance, which flags carry what changes, and whether the write is sparse or a full replace. `properties` is typed over the command's own declared names with a floor of one, so a property naming a flag the command does not declare -- and an empty list -- are compile errors. The framework enforces that at least one property is supplied, renders the write set on every surface a run reports through (one unnumbered line in the would-do log and a `writes` member on the machine envelope), and publishes the declaration in `--dump-schema` and in the MCP tool schema. A property declares `presence: "optional"`: absence means untouched, and `nullable: true` mints `--unset-<prop>`, answered by `ctx.unset(name)`.
- [ts-strictcli] **The package README documents the update-command construct.** A features entry covers `updateOf`, its `properties` tuple typed over the command's own declared names, the mutating-default ban, the at-least-one-property rule, the write set's two renderings and the minted `--unset-<prop>` spelling; the config entry carries `config set`'s reshaped `--value` argv.

### Fixes

- [ts-strictcli] **A declared default never runs a flag's `validate` callback, and never counts as supplied.** A validator now sees only values the invocation caused -- CLI, env, config or an implication -- so a default the validator would reject no longer fails the parse when nothing is typed. The same one predicate decides presence for `allOrNone`, `requires` and `implies`, and it now excludes the `infra` source (a `relativeToRoot` default resolved through a declared root), which is the declaration deciding just as a plain default is.
- [ts-strictcli] **A structural parse problem is now reported ahead of a value that will not parse.** An unknown flag, an unknown choice and a scope violation are facts about the command line's shape, and shape is decided before any token's text is interpreted -- on every command, not only on one that declares a choice flag. `myapp cmd --count abc --unknown` reported `--count: expected integer, got 'abc'` and now reports `unknown flag '--unknown'`, and the answer no longer depends on which token came first.
- [ts-strictcli] **The MCP tool schema describes array parameters correctly.** A parameter whose value is a list carried its `enum` at the property root, which said the array itself had to equal one of the choices; it now sits inside `items`, describing an element. The projection derives its shape from the same arity rule the dumped `value_schema` fragment states, so a tool schema and a dumped schema cannot disagree.
- [ts-strictcli] **A positional arg with helped choices renders an indented block.** The block rule was always content-keyed -- any `choices` entry carrying help -- and it now reaches positional args exactly as it reaches flags: the entries render beneath the arg's line with their help, the one-line `[choices: a, b]` part is dropped in that form, and one alignment column is computed across the whole `Arguments:` section. A defaulted choice flag also renders its complete elected value (`[default: webhook (url=..., retries=5)]`) instead of the bare choice name, and a member-spelled choice flag's line carries its bare name with each member line ending in its own presence part.
- [ts-strictcli] **A member's payload property elects that member over MCP and `asTools`.** The flat machine form has no tokens, so supplying the property that flattens under a member's own flag name is that election: `{"profile": "work"}` now elects `--profile` and carries its value, exactly as `--profile work` does on the command line, without repeating the choice under the selector's own property. Supplying one member's payload beside a selector property naming a different member is a double election and is refused with the CLI's own sentence -- `--profile and --all-profiles are mutually exclusive` -- instead of a scope refusal that named the member's own election as the scope it was missing from. One level down the same rule holds: a payload key under an unelected outer scope names that outer scope, byte-for-byte as the parser does.
- [ts-strictcli] **A member name colliding with a command-level flag is reported as the duplicate flag name it is.** Electing a member IS the election, so a member's own name is a root token that opens no scope of its own. Declaring `memberChoiceFlag("mode", { profile: ... })` beside a command flag named `profile` -- or two member-spelled choice flags that both declare a `profile` member -- now raises `command "run": duplicate flag name "profile"` instead of the simultaneously-electable message, which could only state the collision with two empty scope paths. A member may still carry its own selector's name, which is never typed under member spelling, and a nested member colliding with a command-level flag keeps the scoped diagnosis.
- [ts-strictcli] **A refusal inside nested scopes names the outermost election that came from outside the command line.** A required sub-flag missing under two nested choice flags blamed the innermost election, so a scope elected from an environment variable beside a typed inner one said nothing at all about the variable that caused it. The clause now walks the scope path outermost first and names the first election that did not come from the command line -- `(elected from env var 'MYAPP_VISIBILITY')` -- and stays absent when every election on the path was typed.
- [ts-strictcli] **The flat machine form MCP and `asTools` take answers with the command line's own sentences.** Three refusals were wrong at that boundary. Elections ran one selector at a time, so an earlier selector's missing election was reported ahead of a later one's double election -- `{target: "all-profiles", profile: "work"}` on a command declaring a required `mode` first said `one of --fast, --slow is required` where the same command line says `--profile and --all-profiles are mutually exclusive`; every election now resolves command-wide, at every depth, before any scope, value or presence problem is reported. Electing a payload-carrying member through the selector's own key without its payload -- `{target: "profile"}` -- said `flag '--profile' is required under '--profile'`, naming the flag as its own owner, and is now `flag '--profile' requires a value`. And a payload-less member's own property was ignored, so `{all_profiles: true}` was refused with `one of --profile, --all-profiles is required` where `--all-profiles` elects; it now elects on `true` and declines on `false` exactly as `--no-all-profiles` does, decline clause and redundant-negation refusal included. A selector one level down also names the scope it sits in when it refuses, as it does on the command line.
- [ts-strictcli] **A record handed to `app.call()` electing a member with no `value` takes the same missing-value sentence.** `app.call("fetch", { source: { choice: "url" } })` reported `flag '--url' is required under '--url'`; a member flag is elected by its own token and that token carries the payload, so the refusal is now `flag '--url' requires a value` at both front doors.
- [ts-strictcli] **The machine boundary and `app.call()` answer with the command line's own sentences, in the command line's own order.** Four refusals were wrong. A key naming nothing the command declares was checked only after the selectors had been converted, so it lost to whatever that work found -- `{via: "email", nope: 1}` reported a missing election where the same command line reports `unknown flag '--nope'`; it is a fact about the object's shape and now outranks every election, scope, value and presence problem, at both doors, and a nested selector's own property is recognized so supplying one under a sibling scope is the out-of-scope refusal rather than an unknown-key one. `one of --profile, --all-profiles is required` put the decline note between the requirement and the scope it lives in and left out the clause naming the environment variable that elected that scope; the three clauses now compose as scope, then origin, then the decline note. A `relativeToRoot` default declared inside a choice's scope was delivered as the marker object itself where the same declaration at command level delivers the resolved path; it now resolves through the declared infrastructure root at every depth. And a pre-typed value is now checked against the type its declaration names -- at command level, inside a scope, on a member's payload and on an app-level global -- so `{count: "7"}` on an `int` flag is `--count: expected integer, got str` rather than a string handed to a handler, and `null` is a legal value for nothing: a flag that may be absent declares `presence: "optional"` and is delivered absent when the key is omitted.
- [ts-strictcli] **`app.call()` checks a positional arg's value, and stages its phases over the whole command.** A positional was stringified on the way in, so `{ count: "7" }` reached an `int` arg as the integer 7 and `{ name: 123 }` reached a `str` arg as `"123"`; an arg is a declaration exactly as a flag is, so the supplied value is now checked against the type it declares -- `argument 'count': expected integer, got str` -- every element of a variadic arg is checked on its own, and `null` is a legal value for nothing. The record door also walked one selector to its end before starting the next, so every stage below election was decided for one selector before the next selector's record was read: a value, a presence or a scope problem in the first record was reported ahead of a second selector's election refusal. Elections, record shapes, scopes, values and presence are now staged across the whole command at every depth, the lowest stage decides what is reported, and the value sweep runs in declaration order rather than the order the caller happened to write the object's keys.
- [ts-strictcli] **A required bool inside a scope names the tokens that satisfy it.** `flag '--verify' is required under '--via email'` left a reader looking for a value to type, where the same declaration at command level says `flag '--verify' must be passed as --verify or --no-verify`. The scoped form is now the root sentence plus the scope suffix -- and the origin clause after it, when an ambient election put the requirement there -- on the command line and at both programmatic front doors alike.
- [ts-strictcli] **A dash-spelled key is refused at `app.call()` too, and a wrong-typed value is heard before a missing election.** `call("run", { "dry-target": "x" })` was accepted and delivered where the same key at the flat machine form is `unknown parameter "dry-target" for command "run"`: a flag's dashed spelling is its command-line token, and both doors take the underscored parameter name the schema publishes. The pre-typed value check also ran downstream of the flat form's conversion, so `{ via: "email", retries: "nope" }` on a command with a second required selector reported the missing election instead of `--retries: expected integer, got str`; the check now runs in the value phase at both doors, ahead of presence and behind every shape, election and scope fact.
- [ts-strictcli] **A key an elected record's scope does not declare is refused, and a pre-typed positional binds to the arg its key names.** `call("run", { via: { choice: "email", retries: 1, bogus: 2 } })` recorded a scope violation spelling the key as a flag -- `flag '--bogus' is only valid under '--via email'` -- for a key naming nothing the command declares anywhere. A record's key namespace is the elected choice's own scope, so the answer is now `unknown parameter "bogus" for command "run" under '--via email'`, at every depth and carrying the whole scope path, reported ahead of every election, scope, value and presence problem in the same call; a flag a sibling scope declares is an unknown key inside a record too, while the same parameter at the flat form's top level keeps the out-of-scope sentence it already had. A scoped refusal two levels down also named only its innermost election, where the command line names the whole path. And positionals handed to `call()` were read densely in declaration order: on a command declaring an optional `label` before a required `count`, `call("run", { count: 2 })` bound 2 to `label` and answered `argument 'label': expected string, got int` -- a sentence about a key the caller never wrote. A value now binds to the arg its key names, and an omitted key is the absence presence answers.
- [ts-strictcli] **Two record-door refusals corrected.** An explicit `null` or `undefined` on an *optional* scoped field at `app.call()`'s record door now delivers absence -- a present field holding nothing -- instead of failing as a type error; that is how a caller writes an unset optional property, and required fields, defaulted fields and the flat door are all unchanged. And a `RelativeToRoot` naming an undeclared infra root inside a choice scope now says where it was declared (`... under '--via email' (elected by default)`) at every door instead of naming no scope at all.
- [ts-strictcli] **The command line's value phase now reports in the order the tokens were typed.** `myapp run --via email --retries nope --before nope` named the root flag (`--before`) whatever the order, because every root flag's value was resolved before any scoped one; both refusals are true, and the one printed is now the token that comes first. A scoped `validate` callback can no longer refuse ahead of a later token's coercion failure either -- every coercion failure is reported before any callback refusal, whatever the declaration order. `call()` and the flat machine form are unchanged: they sweep the command's declarations once, as they always have.
- [ts-strictcli] **A selection nobody elected now reports the declaration at the flat machine door.** A command whose selector declares a default was delivered through `asTools()` / MCP with `ctx.source('via')` answering `cli` and `ctx.provided('via')` answering true, even when the caller sent nothing at all -- where the command line and `call()`'s record form both answer `default` and false for the same declaration. All three doors now agree. A scoped flag supplied beside a defaulted election is still delivered, exactly as the command line delivers it.
- [ts-strictcli] **`config show` renders a `RelativeToRoot` default as the declaration.** The human table printed the marker object's internals -- its fields plus the source text of its `toString` -- instead of `db = RelativeToRoot('MYAPP_HOME', 'db.sqlite')  (source: default)`, which is what the other implementations print byte-for-byte. Under `--json` the payload carried the runtime's own casing; it now carries the machine-stable shape `--dump-schema` already uses, `{"relative_to_root": {"env_var": ..., "parts": [...]}}`. The resolved path is unchanged where it belongs: a run still delivers it, labelled `infra`.
- [ts-strictcli] **A refusal from a default-elected scope names what elected it at the flat machine door too.** A `RelativeToRoot` naming an undeclared infra root inside a selection nobody elected read `... under '--via email'` through `asTools()` / MCP, where the command line and `call()`'s record form both read `... under '--via email' (elected by default)` -- the clause exists to name the cause a reader cannot see in their own call, and a conversion is not a caller. Every scoped refusal at that door now carries it, at any depth, naming the outermost election no caller made. A caller's own election still earns no clause.
- [ts-strictcli] **A scoped value supplied at the flat machine door runs its `validate` callback.** A `validate` declared on a flag inside a choice's scope never ran for a value supplied through the flat machine form -- `tools/call` over `--mcp`, and a tool descriptor's `execute` -- so `{ via: "email", subject: "hi" }` was accepted where the same values typed as `--via email --subject hi` are refused with `--subject: hi is refused`. The callback is a property of a supplied value, and this door reads the caller's own keys, so it now runs for a scoped value exactly as it does for a root-scope one and for a typed token: at every depth, per element for a list, and never on a value the declaration decided. A coercion failure still outranks a validate refusal whatever the declaration order. `call()`'s record door is unchanged -- a constructed scope cannot tell a field the caller wrote from one it filled in, so it keeps the type check alone.
- [ts-strictcli] **A scoped value supplied at the flat machine door is checked against its `choices` list, and reports the call.** A closed set declared on a flag inside a choice's scope never constrained a value supplied through the flat machine form -- `tools/call` over `--mcp`, and a tool descriptor's `execute` -- so `{ via: "email", fmt: "xml" }` was accepted where `--via email --fmt xml` is refused with `--fmt: invalid value 'xml', must be one of: text, json`. A supplied scoped value now answers to the whole declaration there: the type, the closed set and the `validate` callback, with a coercion failure outranking both and an earlier field's callback outranking a later field's closed-set refusal. `provided()` over such a value now answers **true** with source `cli` too, as the command line answers for the same value -- that door reads the caller's own keys, so it no longer inherits the record door's uniform `default`. `call()`'s record door is unchanged.
- [ts-strictcli] **Registration reports the first error the contract pins when a constraint set has two faults.** The `Requires` / `Implies` operand guards ran early enough to outrank a required-member refusal, so an `Implies` whose trigger is not a bool was reported ahead of a co-occurrence member declaring `presence: "required"`. Those guards now run after every co-occurrence step, matching the Python and Go implementations.
- [ts-strictcli] **A constraint naming a member-spelled selector's election flag now says so.** `allOrNone`, `atLeastOne`, `requires` and `implies` reported `--all-profiles` as an unknown member or an unknown flag. The flag exists -- it is the token that opens its own scope -- so it now takes the scoped-operand refusal naming that scope, byte-identical to the sibling implementations.
- [ts-strictcli] **Registration reports the pinned first error when a constraint set has both a shape fault and an arity fault.** A bare-string member in a later constraint was reported only after an earlier constraint's "must declare at least two members" refusal. The member-record-shape check now runs across the whole set before any constraint's members are counted, so the bare name is named first -- matching the Python and Go implementations. Both faults are compile errors for a typed caller; the change is visible to a widened or JSON-shaped one.
